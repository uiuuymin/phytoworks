# Development Workflow

## 기본 흐름

```text
main
↓
Orca에서 작업용 Git worktree 생성
↓
Codex가 AGENTS.md와 관련 Wiki 문서 읽기
↓
현재 상태 조사
↓
task 작성
↓
계획 검토
↓
구현
↓
테스트
↓
VS Code에서 직접 코드 확인
↓
Orca에서 diff 검토
↓
task / ADR / domain 문서 업데이트
↓
commit
↓
검토 후 main 병합
```

## 각 단계가 필요한 이유

### 1. main을 출발점으로 확인

`main`은 검토를 통과한 기준선이다. 새 작업이 어느 commit에서 시작하는지 확인해야 이전 작업과 현재 작업의 차이를 설명할 수 있다. 사용자의 명시적 요청 없이 `main`에서 직접 기능을 구현하지 않는다.

### 2. Orca에서 작업용 Git worktree 생성

작업별 branch를 별도 폴더에 checkout하면 현재 작업을 다른 기능과 섞지 않고 진행할 수 있다. Orca는 이 worktree, 터미널과 Codex 세션을 함께 관리해 작업 맥락을 눈에 보이게 한다.

### 3. 규칙과 Wiki 읽기

Codex는 먼저 `AGENTS.md`, `docs/context/index.md`, 관련 domain·ADR·task를 읽는다. 이전 세션의 대화에 의존하지 않고 저장소에 남은 지식을 기준으로 작업하기 위해서다.

### 4. 현재 상태 조사

Git 상태, 기존 파일, 실행 구조와 유사 구현을 확인한다. 조사 없이 만든 계획은 이미 존재하는 패턴을 무시하거나 사용자 변경을 덮어쓸 수 있다.

### 5. task 작성

Goal, 완료 조건, 현재 상태, 관련 지식과 범위를 기록한다. 한 작업이 무엇을 해결하는지 명확해야 diff와 검증도 작게 유지된다.

### 6. 계획 검토

구현 후보의 장단점과 선택 이유를 사람과 AI가 확인한다. 되돌리기 어려운 결정이라면 구현 전에 ADR이 필요한지도 판단한다.

### 7. 구현

승인된 계획의 최소 범위만 변경한다. 새 사실이나 문제가 발견되면 숨기지 않고 task와 계획을 갱신한다.

### 8. 테스트

변경에 맞는 typecheck, lint, unit, API, integration과 수동 검증을 실행한다. 자동 테스트 하나만 통과했다고 전체 사용자 흐름이 맞는 것은 아니다.

### 9. VS Code에서 직접 코드 확인

사용자가 최종 코드를 읽으며 구조, 이름, 학습한 기술의 역할과 의도하지 않은 복잡성을 확인한다. AI가 생성한 코드를 그대로 받아들이지 않는 단계다.

### 10. Orca에서 diff 검토

변경된 파일 전체와 작업 범위를 한눈에 비교한다. 예상하지 못한 파일, secret, generated output 또는 관계없는 리팩터링이 들어오지 않았는지 확인한다.

### 11. 지식 문서 업데이트

실제 구현과 Wiki가 다르면 다음 작업의 출발점이 잘못된다. 변경된 domain 규칙, Accepted 결정, task 결과와 반복적인 workflow 교훈을 각각 알맞은 문서에 반영한다.

### 12. commit

코드, 검증 결과와 관련 문서가 한 의미 단위로 준비된 뒤 commit한다. 이 저장소의 모든 commit 메시지는 한국어로 작성한다. Codex는 사용자 요청 또는 승인 없이 commit하지 않는다.

### 13. 검토 후 main 병합

작업 branch의 결과를 검토한 뒤에만 `main`에 합친다. 병합 방식과 branch/worktree 정리 방법은 팀 규칙이 정해질 때까지 `TBD`다.

## 반복 원칙

각 작업은 `맥락 확인 → 문제 정의 → 접근 검토 → 이유 기록 → 구현 → 테스트 → diff 검토 → 시행착오 기록 → 문서 업데이트 → commit`을 독립적으로 반복한다. 이전 task가 컸다는 이유로 다음 task까지 한꺼번에 구현하지 않는다.
